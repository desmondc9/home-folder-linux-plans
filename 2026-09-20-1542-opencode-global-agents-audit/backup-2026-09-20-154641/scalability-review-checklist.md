# 系统 Scalability 审查清单

> **用途**:排查/评审一个系统的可扩展性时,按顺序过一遍下面的检查项。清单覆盖容量预估 → 应用设计 → 数据层 → 异步化 → 韧性 → 观测 → 验证的整条链路,按实际做架构评审时的考虑顺序排列——单点的慢查询/索引/缓存/并发/OLTP-OLAP 分离只是其中一环,不是全部。
>
> **三个使用时机**(与 `~/.config/opencode/AGENTS.md` 的开发流程对齐):
> 1. **前期规划设计(Step B/C)** —— 先做 §0(容量 + infra 家底),把数字和硬限制写进 `spec.md`;设计方案必须能对上这些数字。
> 2. **实现期(Step D)** —— §1–§8 当作编码红线,尤其 §3 数据层反模式。
> 3. **验收期(Step G,强制)** —— 走 §12「Verify 阶段性能门禁」,逐条收口后才允许提 PR。
>
> 索引入口在 `~/.config/opencode/AGENTS.md` 开发流程的 **Step B / Step D / Step G** —— 三处分别指向本文的 §0、§1–§8、§12。
>
> **最后更新**:2026-08-30(新增 §0.1 监控取数、§0.2 infra 家底盘点、§12 verify 门禁,以及一批来自真实生产事故的教训)

## 0. 先定量:容量预估(一切的前提)

> 很多"scalability 问题"其实是没算清楚容量就上了错误的方案。但**容量预估的前提是有真实数据**——所以先解决"数据从哪来"(§0.1)和"分母是多少"(§0.2),再回答数字(§0.3)。

### 0.1 数据从哪来:先查可观测性平台,查不到再问人

**决策顺序(不要跳过前面几档直接去问用户):**

| 顺序 | 数据源 | 什么时候用 |
|---|---|---|
| ① | **已接入的 APM / 监控平台**(GCP Cloud Monitoring、Azure Monitor / Application Insights、Grafana+Prometheus、Datadog、New Relic、SkyWalking…) | 系统已上线且我有访问权限 —— **默认走这条**,直接拉真实 QPS / 延迟分位 / 实例数 / 错误率 |
| ② | **数据库自带的统计视图** | 要定位"哪条 SQL 慢、扫了多少行、执行了多少次" —— 监控平台通常只到接口粒度,DB 侧统计才到语句粒度 |
| ③ | **网关 / LB / CDN 访问日志** | 要看真实流量形状、状态码分布、被网关拦掉的请求(这些**永远不会**出现在应用日志里) |
| ④ | **前端 RUM / 错误上报**(Sentry、GCP Error Reporting、自建 beacon) | 要看用户真实体感(白屏、ChunkLoadError、首屏时间)—— 服务端指标看不见这一层 |
| ⑤ | **压测数据 / 相似系统的历史数据** | 系统还没上线,但有可比的参照物 |
| ⑥ | **问用户** | 前五档都拿不到时才走这条,且要**问具体的**(见下面的问卷),不要问"你们大概多少量" |

**先确认访问权限再动手**:用**只读**账号/配置(如 gcloud 独立 configuration + 只读 SA、Azure Reader 角色、Grafana viewer),并把用的是哪个环境/项目写进记录。生产只读探查是常规操作,但**任何写操作(建索引、改配置、重启)都要先跟用户确认**。

**都拿不到时,问用户这几个具体问题**(而不是"你们量大吗"):

1. 有没有接监控/APM?叫什么?我能拿到只读访问吗(或者你能帮我导出一段时间范围的数据)?
2. 日均订单/请求/消息条数量级?一天里的峰值在什么时间点,峰值是均值的几倍?
3. 核心业务表现在多少行?一个月长多少?
4. 现在用户觉得慢的具体是哪个页面/接口?什么时候开始的?
5. 上一次出容量事故是什么场景?怎么恢复的?

#### 取数方法学:七个已经踩过的坑

1. **窗口至少取两档:24h + 30d。** 只看 24h 很可能**正好错过故障期**——实战中一次"AU 用户反映慢"的调查,24h 窗口只看到 p95 轻微偏高,拉到 30 天才发现是 06-13→06-23 的一段有明确边界的**回归**(峰值日 p95 28.9s),而调查当天已经恢复了。
2. **分位数按天对齐算,不要把 30 天压成一个桶。** 单桶 `ALIGN_PERCENTILE` 会算出与每日趋势自相矛盾的失真值(同一份数据算出 p50=11.7s,而每日趋势显示大部分天在 300–500ms)。
3. **剔除"设计上就长耗时"的基线。** change-stream / 长轮询 / SSE / WebSocket / 健康检查,天然 avg 好几秒。实战中数据库"总耗时榜"前两名全是 change-stream 分区读(avg 6s × 数百万次),扫描行数其实只有 2 行——不过滤掉就会把治理精力浪费在正常行为上。统计时显式排除(如 `text NOT LIKE 'SELECT * FROM READ_T%Stream%'`)。
4. **服务端延迟 ≠ 用户体感。** 服务端指标不含客户端 RTT。后端在美东、用户在澳洲,单次调用就 ~200–250ms;一个页面串行十几个 API 就累积成"页面很慢",这部分**调优消不掉**,只能靠就近部署/CDN/减少串行往返。
5. **有些故障延迟指标完全看不见。** SPA 陈旧 chunk 的 404 返回极快(max 0.07s),Cloud Run 延迟指标全绿,但用户在白屏。**唯一信号是 `/js|/css` 上的 4xx 计数** + 前端 RUM。凡是"用户说慢/卡但监控全绿",先怀疑这一类。
6. **把发版时间线叠到延迟趋势上。** 回归常常与某次发布强相关;`revisions list` 是最省事的二分工具——实战中直接定位到"06-12 发版引入、06-24 发版消除",把排查范围缩到两个 revision 之间的 diff。
7. **平均值骗人,要看 avg × 执行次数。** "单条慢"(一条 167s)和"量大而单条快"(573 万次 × 0.03s)是两种完全不同的病,治法也不同。排序一律按**总耗时 = avg_latency × execution_count**,再分别看 avg 和 count。

### 0.2 摸清 infra 家底(容量预估的分母)

没有 infra 清单就没法回答"现在的配置能扛多少",容量预估就成了空中楼阁。**这一步产出一张实测快照表,不是凭印象**。

**盘点清单**(每项都记:实测值 / 取值命令 / 环境差异 / 快照日期):

| 层 | 要盘的东西 |
|---|---|
| **计算** | 服务清单;每服务 CPU / 内存;min / max 实例数;**单实例并发度**(Cloud Run `containerConcurrency`、K8s replica × worker 数、Tomcat 线程池);请求超时;启动探针配置;CPU 是否 throttling / 是否开 startup boost |
| **数据库** | 引擎与版本;节点数/规格;单区还是多区;是否有只读副本;连接池上限;当前存储量;**Top N 大表的实际行数**;每张热表的二级索引清单 |
| **缓存** | Redis/Memcached 规格、是否 HA、内存上限、逐出策略、是否分片、当前命中率 |
| **消息** | topic / subscription 清单;**push 还是 pull**;ack deadline;死信队列与重投策略;消费者并发度;当前积压 |
| **网关 / 边缘** | LB 类型与超时;**WAF 规则集**(这是可用性风险,见 §8);API 网关(ESPv2 / APIM / Kong)配置与超时;CDN;**请求体大小上限** |
| **存储** | 对象存储桶清单、生命周期规则、是否直传 |
| **批处理 / 调度** | 定时任务清单**和触发时刻**——多个 job 撞在整点是峰值叠加的常见源 |
| **网络** | VPC / 子网 / 连接器;**服务所在区域 vs 用户地理分布**(跨洋 RTT 是结构性延迟) |
| **环境阶梯** | dev / uat / prod 的规格差异。**dev 通常是沙箱**(含大量临时资源),不作架构基准;以 uat/prod 为准 |
| **配额与硬限制** | 见下方专表 |
| **成本** | 自动扩缩容的上限设了没有(配置错误或被刷时的账单护栏) |

**怎么做**:用只读凭据 + 平台 CLI 一次性遍历(`gcloud <service> list`、`az <service> list`、`kubectl get`、`terraform show`),把结果整理成架构文档里的一节(标注"实测快照 + 日期 + 复现命令"),后续所有容量讨论都引用它。这份清单一旦存在,复用价值极高——它同时是发布、排障、成本审查的基准。

**必须显式记录的"硬限制"**(这些看起来与性能无关,却是批量接口在生产上炸掉的头号原因):

| 类别 | 常见限制(以实际平台文档为准) |
|---|---|
| 单条 SQL 参数上限 | Spanner ~950;Oracle `IN` 列表 1000;PostgreSQL 65535;SQL Server 2100 —— **批量 INSERT/UPDATE/IN 查询必须按此分块** |
| 请求超时 | Cloud Run 默认/上限、ALB/Nginx 默认 60s、API 网关超时 —— 各层要一致,别让内层比外层还长 |
| 请求体 / 响应体大小 | API 网关、WAF、LB 各有上限;大 payload 走对象存储直传 |
| 消息中间件 | 单条消息大小、ack deadline、单订阅未确认消息数上限 |
| 缓存 | 单 key / 单 value 大小、maxmemory 与逐出策略 |
| WAF / 安全策略 | 上传路径白名单约定、请求体形状规则(见 §8) |
| 平台配额 | 每项目实例数、连接数、并发构建数、API 调用配额 |

### 0.3 要回答的数字

有了 §0.1 的数据和 §0.2 的分母,回答这几个数字,否则优化没有靶子:

- 预期 DAU / 峰值 QPS 是多少?读写比多少?
- 数据量级和增长速度(单表一年长到多少行)?
- 延迟目标:P50 / P99 分别要求多少 ms?**用户侧**还是**服务端**口径?
- 峰值是持续的(电商大促)还是脉冲的(整点推送 / 定时任务撞车)?
- 可用性目标:几个 9?允许的最大 RTO/RPO?
- **当前配置的理论上限是多少**(实例数 × 并发度、DB 节点数、连接池大小),离目标还有几倍余量?
- 多租户/多区域系统:**单租户最大值**是多少(不是平均值)?最大的那个租户会不会先撑爆?

## 1. 应用层:能否水平扩展

- [ ] **服务无状态化**:session、本地缓存、本地文件都不能依赖单机(session 放 Redis、文件放对象存储)
- [ ] 实例可以随便加、随便杀(配合 K8s HPA / 云 Auto Scaling)
- [ ] 本地缓存只用作优化,不作为正确性依赖(多实例间数据不一致要能接受)
- [ ] 长耗时操作不放请求线程里(见第 5 条异步化)
- [ ] **单实例并发度是个真参数,不是越大越好**:`containerConcurrency=1000` 配 6–8 vCPU,意味着上千请求挤同一份 CPU;慢请求一堆积就互相挤占、尾延迟放大,而 autoscaler 因为"实例还没满"迟迟不扩容。宁可调低并发度(如 80–200)让它多开实例。

## 2. API 设计层

- [ ] **分页**:所有列表接口强制分页,禁止 `SELECT *` 全量返回;深分页用 cursor/keyset 而不是 `OFFSET 100000`
- [ ] 字段裁剪:避免一个"大而全"的接口被所有场景复用(必要时 GraphQL / 稀疏字段集)
- [ ] 幂等设计:写接口支持幂等键(Idempotency-Key),防止重试造成重复扣款/下单
- [ ] 批量接口:提供 batch 端点,避免客户端循环调用;**同时给出批量上限**(并对齐 §0.2 的 DB 参数上限)
- [ ] 响应压缩(gzip)、避免 N 次往返的 chatty API —— 一个页面串 15 个 API,在跨洋场景直接等于 15×RTT
- [ ] **传输契约别做双重编码**:把结构体 `JSON.stringify` 后当字符串塞进 JSON body,除了浪费带宽,还会让转义后的内容命中 WAF 规则(见 §8 实战)

## 3. 数据层

**查询与索引**
- [ ] **多租户系统:每条读和每条写都要带租户/hub 谓词。** 缺谓词的语句既是跨租户越权,也往往就是那条全表扫描 —— 两件事同一个根因。租户身份只从服务端可信来源(JWT/会话)取,客户端传来的租户 ID 只能当过滤输入、**不能当授权依据**;确实需要跨租户的语句,给**独立命名的方法** + 注明唯一合法调用方 + 单测锁定;无租户上下文时 **fail closed**,不要退化成不带谓词的查询。(它为什么同时是安全问题,见 §11)
- [ ] 消灭 N+1(ORM 开 SQL 日志定期审查;用 join fetch / batch fetch / Dataloader 模式)。**特别检查:已经存在批量方法却没被用**(`findByIds` 就在旁边,resultMap 里还挂着逐行 `select=`)
- [ ] 慢查询日志常态化开启,设阈值告警(如 >500ms)
- [ ] 索引覆盖高频查询的 WHERE + ORDER BY,注意最左前缀;定期清理无用索引(拖慢写入)
- [ ] **双向审索引,别只看一头**:实战中同一个库里同时存在两种病——热表(outbox、集成日志、业务主表)**一个二级索引都没有**,导致 92 万~5590 万行全表扫描;而另外两张表各有 **54 / 46 个索引**,写放大严重却仍然命中不了聚合查询。用 `INFORMATION_SCHEMA` 拉全量索引 + 用索引使用统计找从没被用过的。
- [ ] **索引上线是独立的写操作,要与代码发布解耦**:大表 `CREATE INDEX` 有 backfill 成本,应分批、在低峰、可回滚地做,并且**只给需要的租户/国家建**(多租户系统里"某国专用索引"建到别的国家是错的)。发布前用"定义清单 vs 真实库清单"做差集校验,别假设索引已经在了。
- [ ] 大表禁止全表扫描;**杜绝非 SARGable 谓词**:
  - 前导通配 `LIKE '%xx'` / `LIKE CONCAT('%',?,'%')` —— 天然无法用索引,实战中单条扫过 5590 万行。能前缀匹配就改 `STARTS_WITH` / `LIKE 'x%'`;真需要"包含"语义就上全文/搜索索引
  - 函数包裹索引列:`UPPER(col) LIKE ...`、`PARSE_DATE(FORMAT_TIMESTAMP(col))`、`TRIM(col)!=''` —— 改存规范化列或预计算列
  - 否定/不等式:`status != 4`、`x IS NULL OR x = false`
  - `NOT IN (不相关子查询)` 反连接 —— 改 `LEFT JOIN ... WHERE x IS NULL` 并给连接键建索引
  - `STRPOS(a,b) > 0` 之类非等值连接 —— 强制全表笛卡儿,必须改成规范化关联键的等值连接
- [ ] `ORDER BY ... DESC` **必须配 LIMIT / keyset**;`COUNT(*)` 大表慎用,用近似计数或汇总表
- [ ] **动态 SQL 一律用绑定参数,不要字符串拼值**:除了 SQL 注入,拼值会让每个不同的值生成不同 SQL 文本,**击穿数据库的查询计划缓存**(每次重新编译)。`${}` 只留给白名单校验过的标识符(列名、排序方向)
- [ ] **无界查询**:全可选的 `<where>` 退化成全表 `SELECT`;`findAll()` 加载整表再在内存里过滤(实战中同一个服务里有 8 处,而下推过滤的方法就在旁边);无界 `IN (应用传入的列表)`
- [ ] **批量 DML 按参数上限分块**(见 §0.2 硬限制):一次 `saveAll` 150 行 × 12 列 = 1800 个参数,超过引擎上限直接报错;固定成"每块 ≤N 行"的工具方法,并**写一个断言分块数量的单测**

**连接与拓扑**
- [ ] 连接池(HikariCP 等)大小按 `connections ≈ ((core_count × 2) + effective_spindle_count)` 量级估算作为起点,不是越大越好(该公式源自机械盘时代,SSD/云盘环境下仅作为初始参考,最终要靠压测调优)
- [ ] 读写分离(读流量打到只读副本)
- [ ] **只读报表/列表/导出用陈旧读**:能容忍秒级陈旧的场景用 bounded-staleness / exact-staleness / 只读副本,把读流量从主节点卸掉。实战审计发现某系统 **0 处**使用陈旧读,报表全打在强一致读上
- [ ] 单库到极限后的拆分路径:垂直拆分(按业务)→ 水平分片(sharding);ShardingSphere / Vitess / 云原生分布式库(Spanner、TiDB、CockroachDB)
- [ ] 冷热分离:历史数据归档到便宜存储

**数据结构与模型**
- [ ] 范式 vs 反范式权衡:读多写多场景适当冗余,避免大 join
- [ ] JSON 列、大 TEXT/BLOB 与主表分离
- [ ] **过宽投影**:热点点查取 183 列的 `Base_Column_List`、`SELECT *` 子查询物化全列 —— 百万次/天的路径上会显著放大网络与内存。显式列出需要的列,热点路径用覆盖索引(STORING/INCLUDE)

**写正确性(高并发下才暴露)**
- [ ] **乐观锁要覆盖"所有"写路径**:同一张表如果既有 ORM `repo.save()` 又有手写 SQL,两条路都必须遵守 `version` 检查,否则 ORM 那条路会不声不响地覆盖掉别人的更新。实战审计:533 个手写 update 只有 95 个带 version 保护;24 个有 version 列的实体只有 1 个加了 `@Version`
- [ ] 有意豁免乐观锁的批量/强制写路径,**在代码注释里写明豁免理由**(防重的唯一约束兜底见 §6)

**审计方法**:治理这类问题不要抽样看,**做全量机械扫描再与生产慢查询对账** —— 用 ripgrep 统计每种反模式的出现次数(`SELECT *` 96 处 / 前导 LIKE 295 处 / `OFFSET` 249 处…),同时从数据库统计视图拉真实慢查询,把两边对上,才知道哪些反模式是真痛点、哪些只是理论问题。

## 4. 缓存层

- [ ] 识别真正的热数据再缓存(缓存命中率要可观测,低于 ~80% 的缓存可能得不偿失)
- [ ] **缓存穿透**:空结果也缓存(短 TTL)或布隆过滤器
- [ ] **缓存击穿**(热点 key 失效瞬间):互斥重建(single-flight)或逻辑过期
- [ ] **缓存雪崩**:TTL 加随机抖动,避免同时失效
- [ ] 缓存与 DB 一致性策略明确:Cache-Aside 为主,接受最终一致;强一致场景用延迟双删或 binlog 订阅(Canal/Debezium)
- [ ] **key 粒度由"失效成本"决定,不是由"查询参数"决定**:如果按 `(tenant, date)` 建 key,一次配置修改会让多个 date 同时失效,清理时只能 `SCAN`/`KEYS`(反模式)。改成按 `tenant` 建 key、把 date 过滤放到应用侧,一次 `DELETE` 就 O(1) 失效
- [ ] **缓存故障必须是非致命的**:每处 Redis 读写都包 try-catch —— 读失败退回数据库(记 WARN),写失败不重试(下次 miss 自然重建),绝不因为缓存挂了给用户返 500
- [ ] TTL 用全局默认,不要每处自定义(除非有写下来的理由)
- [ ] 多级缓存:本地缓存(Caffeine)+ 分布式缓存(Redis),注意多实例一致性

## 5. 异步化与削峰(OLTP vs 离线/流式的分界)

- [ ] **请求内能异步的都异步**:发邮件、通知、审计、第三方回调 → 消息队列(Kafka/RabbitMQ/SQS/Pub-Sub),接口立即返回
- [ ] **削峰填谷**:秒杀/脉冲流量先入队,后端按消费能力处理
- [ ] **后台消费者必须与用户请求隔离**:实战中最贵的一次事故就是异步 push-handler 和用户请求**跑在同一批实例上**——handler 调用量暴增 15 倍且每条卡 15s,把并发打满,连坐把所有用户请求的 p95 抬到 6–10s。要么独立 worker 服务/独立部署单元,要么把单实例并发度调低让 autoscaler 加实例而不是单实例堆积
- [ ] **重试风暴与死信是一等风险**:处理超时 → 消息未 ack → 重投 → 更多并发 → 更慢,正反馈直到服务瘫痪。必须有:退避重试上限、死信队列、**消费者幂等**、以及"死信量"这个告警指标
- [ ] **超时预算要跨层对齐**:如果一批请求都精确卡在同一个整数秒(如全部 15.00s),说明存在一个**隐藏的应用层 deadline**(事务超时 / HTTP 读超时 / MQ ack deadline),先把它找出来——它把"慢"变成了"失败→重投→风暴"
- [ ] **定时/批处理**:从 API 进程里剥离,用独立的 worker;调度用 Quartz 集群版 / xxl-job / Airflow / K8s CronJob,按复杂度选。**检查各 job 的触发时刻有没有撞在一起**
- [ ] **报表/分析类查询绝不打 OLTP 主库**:先只读副本/陈旧读,再上 OLAP(ClickHouse / BigQuery / Redshift / Snowflake)。实战中一个仪表盘的四条聚合查询,每条扫 ~210 万行、30 天各执行 ~4 万次(≈每分钟一次的自动刷新),是整个库最大的持续成本。典型解法:change-stream/CDC → 流式增量维护**预聚合汇总表**,前端只读汇总表;注意别留"今天的数据仍走实时全扫"的后门——那正是成本的来源
- [ ] Spark/Flink 只在真正有大规模 ETL 或流式计算需求时引入——中小规模用 Airflow + SQL + OLAP 库足够,别为用而用
- [ ] 事件驱动架构(EDA):跨服务通信用事件解耦,配合 **outbox 模式**保证"DB 写入 + 消息发出"的原子性
- [ ] **outbox 优先用 CDC/change-stream,而不是轮询**;必须轮询时,轮询谓词列(status / created_at)必须有索引且带 LIMIT——无索引的 outbox 轮询是"随数据增长必然爆炸"的定时炸弹

## 6. 并发与分布式正确性

- [ ] 热点资源竞争:库存、余额等用乐观锁(版本号)/ 原子更新(`UPDATE ... SET stock = stock - 1 WHERE stock > 0`),慎用分布式锁
- [ ] 分布式锁(Redisson 等)要设过期、防误删,能不用就不用
- [ ] 唯一约束兜底:业务防重最终靠 DB unique index,不靠应用逻辑
- [ ] 事务边界最小化;跨服务用 Saga / 最终一致,避免分布式事务(XA)
- [ ] **线程池必须是应用级单例 + 有界队列 + 明确的拒绝策略**(如 `CallerRunsPolicy` 天然限流)。**禁止在方法体里 `new` 一个 executor** —— 每次调用现建一个不共享、无上限、可能连 shutdown 都没做的池,外部触发频率一高就是无限制并发爆发
- [ ] **虚拟线程不是"零成本"的免费午餐**(Java 21 场景):
  - JDK < 24 时,虚拟线程在 `synchronized` 块内阻塞会**钉住(pin)carrier thread**;若下游客户端(某些数据库 driver、连接池、Jedis)内部大量用 `synchronized`,虚拟线程池化基本没有意义
  - carrier 池默认大小 = `availableProcessors()`,**且是 JVM 进程级全局共享**。在 CPU 配额很小的容器里(1–2 vCPU),几个 pin 住的虚拟线程就能把全局池清零 → **整个服务冻结**(不是崩溃),连打日志和健康检查的调度机会都没有 —— 症状正是"服务完全无响应且平台上没有任何日志输出"
  - 真要用:应用级单例 bean + `Semaphore`/`StructuredTaskScope` 限流 + 先按生产并发量压测突发场景
- [ ] 检查注释与实现是否已经脱节(代码注释还写着 "using virtual threads",实现早就换成有界池了——会误导下一个人)

## 7. 韧性(高并发下不出事的关键)

- [ ] **超时**:每一层(HTTP client、DB、Redis、RPC、MQ ack)都必须有超时,没有默认值就显式设置;**且内层超时要小于外层**,否则外层先超时、内层还在跑,资源双份占用
- [ ] **重试**:只对幂等操作重试,指数退避 + jitter,限制次数(重试风暴会放大故障)
- [ ] **熔断**(Resilience4j / Polly):下游挂了快速失败
- [ ] **限流**:入口限流(网关层 token bucket)+ 按用户/租户配额;保护自己也防恶意刷
- [ ] **降级预案**:非核心功能(推荐、个性化)可开关,大促时一键关闭
- [ ] **背压**:队列满了怎么办?明确溢出策略
- [ ] 隔离:线程池/连接池按下游隔离(bulkhead),避免一个慢下游拖垮全部
- [ ] **外部集成是隐藏的容量瓶颈**:对第三方系统的调用(串行、无超时、批内逐条往返)会把一个后台 handler 的常态耗时顶到 12–15s,平时看不出来,量一涨就爆

## 8. 边缘与传输层(LB / WAF / 网关 / CDN)

- [ ] 静态资源 / 图片走 CDN
- [ ] HTTP 缓存头(ETag、Cache-Control)减少重复请求
- [ ] 负载均衡健康检查配置正确(摘除不健康的实例);**检查有没有实例因健康检查失败长期回退到旧版本**
- [ ] 大文件上传下载:分片、断点续传、直传对象存储(预签名 URL),别经过 API 服务器中转
- [ ] **WAF / 安全策略是可用性风险,必须纳入评审**:
  - WAF 在 LB 层拦截,请求**根本没到应用**,后端日志里 0 条记录 —— 症状是"前端 403 / 400,后端查不到任何痕迹",千万别在后端找原因
  - 实战一:列配置被 `JSON.stringify` 成字符串塞进 JSON body(双重编码),转义后出现 `\"select\"`,命中 SQLi 特征规则 → 全环境 403。修法是**改传输契约**(数组直传、单层编码),不是放宽 WAF 规则
  - 实战二:multipart 上传的 MIME boundary 命中协议攻击规则,而放行规则要求**路径包含某个约定片段**(形如 `/…-upload/`)—— 新加的上传端点不遵守这个约定就 403。**这类"路径/形状约定"必须写进项目规范并在评审时检查**
  - 改了网关路径要和 API 网关配置(OpenAPI / ESPv2 / APIM)**同步发布**,并注意**发布顺序**:后端先、网关次之、前端最后。顺序反了会出现"新路径路由到旧 jar → 404"
- [ ] **SPA 陈旧 chunk(发版后部分用户白屏)**:hash 命名的 chunk 在新构建里不存在 → 动态 `import()` 失败 → 路由组件挂不出来。三件套:
  1. `index.html` 设 `Cache-Control: no-cache, no-store, must-revalidate`;`/js|/css|/assets` 的 hash 资源设 `max-age=31536000, immutable`(**最关键的一条**)
  2. 前端全局捕获 `ChunkLoadError` → `location.reload()`(用 `sessionStorage` 防刷新死循环)
  3. 发版时保留上一版 chunk 一段过渡期,让发布瞬间在会话中的用户不至于 404
  - 监控:给 `/js|/css` 的 4xx 单独建日志型指标 + 告警(见 §0.1 坑 5)

## 9. 可观测性(没有它,以上全是盲调)

- [ ] 三大件齐全:Metrics(Prometheus / Cloud Monitoring)、Tracing(OpenTelemetry/Jaeger/Cloud Trace)、结构化日志(带 trace ID 串联)
- [ ] 关键指标:RED(Rate/Errors/Duration)每个接口都有;DB 连接池、**队列积压**、**死信量**、缓存命中率、实例数
- [ ] 慢查询、慢接口有专门 dashboard 和告警
- [ ] **前端 RUM 是唯一能看见"用户白屏"的手段**:`window.onerror` / `unhandledrejection` 上报 ChunkLoadError、资源 404、首屏渲染失败,配合 LCP/TTI
- [ ] **日志型指标补监控盲区**:按 URI 模式 + 状态码建计数指标(静态资源 4xx、特定端点 5xx),这类故障在聚合延迟指标里完全不可见
- [ ] 生产开 Profiler(CPU/堆持续采样),否则"CPU 高"只能靠猜
- [ ] 告警基于症状(用户受影响)而非原因,避免告警风暴;SLO + 多窗口烧录率告警降噪
- [ ] **确认异常处理器没有吞掉日志**:实战中全局异常处理器对某几类异常(包装过的 SQL 约束冲突、事务异常)只返回通用错误、**不打任何 error 日志**——查不到日志不等于请求没到过服务端。评审时逐条看 handler 的每个分支有没有 log
- [ ] 排障时**先剔除设计上的长耗时基线**再看榜单(见 §0.1 坑 3)

- [ ] **压测**:上线前用 JMeter / k6 / Gatling 打到目标 QPS 的 2–3 倍,找到拐点;别只压平均,压峰值场景;**单独压异步/消息突发场景**(那是最容易被漏掉、也最容易连坐全站的路径)

## 11. 容易忽略的"长尾"项

- [ ] **时钟与 ID**:分布式 ID 生成(雪花/ULID),避免 DB 自增主键成为分片障碍
- [ ] **数据生命周期**:日志表、集成记录表、outbox 消费日志、临时表必须有 TTL 和定期清理/归档任务。**表无限增长是最常见的慢性死亡**——实战中的百万级集成记录表和数千万级消费日志表,正是全表扫描慢查询的宿主
- [ ] **部署策略**:滚动/金丝雀发布;DB schema 变更向后兼容(先加列后改代码,Liquibase/Flyway 管理);**大表 `ADD COLUMN ... DEFAULT` 的 backfill 可能撑爆启动探针窗口** —— 迁移要与应用启动解耦,单独执行并保留回滚方案
- [ ] **多租户 / 多区域隔离既是安全问题也是性能问题**:同一个缺失的租户谓词,既是跨租户越权、也是那条全表扫描 —— 所以安全评审和性能评审谁都不能指望"对方查过了"。**可执行的编码规则在 §3 第一条**(它属于编码红线,不是长尾项);这里只提醒:排期时把它当一件事做,别拆成两轮
- [ ] **契约字段名是接口的一部分**:序列化框架按 getter 推导出的字段名(如 `gNumber` → `gnumber`)会让前端读到 undefined 且**全链路无任何报错**。非标准 camelCase 字段用注解钉死 + 两侧各写一个契约测试
- [ ] **安全即容量**:鉴权放网关层做、防爬虫防刷(否则机器人流量会吃掉你的容量预算)
- [ ] **成本**:自动扩缩容的上限要设,防止配置错误或被攻击时账单爆炸

## 12. Verify 阶段性能门禁(开发/规划的收口检查)

> 每个功能开发或 bug 修复,在**提 PR 之前**必须过这道门禁(对应 `~/.config/opencode/AGENTS.md` 开发流程的 **Step G**)。目的不是每次都做全量架构评审,而是**保证这次变更不会引入新的性能债**。

### 12.1 触发器:本次变更命中任何一条,就必须逐条回答 §12.2

- [ ] 新增或修改了**任何 SQL / mapper / ORM 查询**(含 report/export/dashboard)
- [ ] 新增或修改了**列表 / 分页 / 搜索 / 导出**接口
- [ ] 新增或修改了**批量写**(batch insert/update、`saveAll`、`IN (...)`)
- [ ] 新增或修改了**定时任务 / 消息消费者 / 异步处理**
- [ ] 新增或修改了**缓存**读写路径
- [ ] 新增或修改了**外部系统调用**(第三方 API、跨服务 RPC)
- [ ] 新增或修改了**上传/下载 / 大 payload / 网关路径**
- [ ] 新增了**表 / 列 / 索引**,或改动了迁移脚本
- [ ] 改动会**显著提高某条既有路径的调用频率**(比如新页面每次加载都调它)

一条都没命中(纯前端文案、纯文档、纯测试重构),**在 PR 描述里写一句"本次变更不触发性能门禁,理由:…"** 即可跳过。

### 12.2 收口检查(逐条给出结论,不是打勾了事)

**查询侧**
1. 这次新增/改动的每条查询,**谓词列和排序列有索引吗**?没有的话,索引在哪个迁移/清单里?什么时候建?
2. 有没有引入 §3 列出的非 SARGable 写法(前导 LIKE、函数包裹列、`NOT IN` 子查询、`!=`)?
3. 列表接口分页了吗?深分页是 keyset 还是 `OFFSET`?`ORDER BY` 带 LIMIT 了吗?
4. 投影是显式列还是 `SELECT *`?热点路径需要覆盖索引吗?
5. **在接近生产的数据量下**估算过扫描行数吗?(不是在 100 行的本地库里跑一下就算)

**写入侧**
6. 批量操作的分块大小是多少?**对齐 §0.2 记录的引擎参数上限了吗**?有断言分块的单测吗?
7. 有 version 列的表,这次的写路径加乐观锁了吗?ORM 和手写 SQL 两条路都覆盖了吗?
8. 租户/hub 谓词在每条读和写上都存在吗?确实要跨租户的地方,是独立命名方法 + 有测试吗?

**异步与并发**
9. 新的消费者/定时任务跑在哪里?会不会和用户请求抢同一批实例/线程池?
10. 超时设了吗(每一层)?和上游 ack deadline / 网关超时对齐了吗?重试有退避和上限吗?死信怎么处理?
11. 用了线程池吗?是应用级单例 + 有界队列 + 拒绝策略吗?

**缓存与契约**
12. 缓存 key 的粒度能 O(1) 失效吗?所有写路径都失效了吗?Redis 挂了会不会 500?
13. 接口契约字段名两侧一致吗(有契约测试)?payload 有没有双重编码 / 超出网关体积或 WAF 规则?

**观测与验证**
14. 这次新增的路径,**出问题时从哪个指标/日志能看出来**?需要补埋点或日志型指标吗?
15. 有没有跑过一次前后对比(至少:本地/dev 上打开 SQL 日志看实际发出的语句数和形状)?
16. 有没有引入"随数据增长会变慢"的结构(无 TTL 的日志表、无索引的轮询、每页重算的 COUNT)?如果有,记为 follow-up 任务并写进 backlog。

### 12.3 产出物

把结论写进本次任务的 `spec.md` / `implementation-[phase].md` 的**「性能与容量」一节**,PR 描述里引用它。内容至少包含:

- 命中了哪些触发器
- 涉及的查询/写入的预估数据量级与扫描量
- 新增/依赖的索引清单(及它们的上线方式)
- 用到的硬限制数字(分块大小、超时、批量上限)及其来源
- 已知的、**有意接受**的性能债 + 对应的 follow-up 工单

## 速查:典型症状 → 首先检查哪里

| 症状 | 第一怀疑对象 |
|---|---|
| 接口越来越慢 | 慢查询日志、N+1、缺索引、表无限增长 |
| 高峰时大量超时 | 连接池耗尽、无超时配置、下游慢、单实例并发度过高 |
| 整点/定时任务后抖动 | 批处理和 OLTP 抢资源、多个 job 撞时刻、缓存同时失效 |
| 重复数据/重复扣款 | 缺幂等、缺唯一约束、乐观锁只覆盖了一条写路径 |
| 某个功能挂导致全站挂 | 缺隔离/熔断、共享线程池、后台消费者与用户请求共实例 |
| 报表查询拖垮主库 | OLAP 流量打到 OLTP 库;没有预聚合/陈旧读 |
| **服务完全无响应,平台上零日志** | 线程/carrier 池耗尽(虚拟线程 pinning、无界 executor);不是崩溃 |
| **一批请求都精确卡在同一个整数秒** | 隐藏的应用层 deadline(事务/HTTP 读/ack deadline)→ 超时→重投风暴 |
| **前端 4xx/403,后端查不到任何日志** | WAF / LB 层拦截,请求没到应用(payload 形状、上传路径约定) |
| **发版后部分用户白屏,监控全绿** | SPA 陈旧 chunk(404 极快,延迟指标看不见);查 `/js\|/css` 4xx |
| **只有某个国家/租户慢** | 该租户数据量、该环境缺索引、跨区 RTT |
| 批量接口本地正常、生产报错 | DB 单语句参数上限、请求体大小上限、网关超时 |
| 列表页越翻越慢 | 深分页 `OFFSET` + 无索引 `ORDER BY` |
| 监控显示 DB CPU 很闲但查询很慢 | 不是容量问题,是单条查询设计问题(扫描量/缺索引/宽投影) |

## 如何使用这份清单

- **完整评审**:从第 0 节到第 11 节顺序过一遍,尤其别跳过 **0(容量 + infra 家底)、1(无状态)、9(观测)、10(验证)** 这四条——最容易被跳过,但恰恰是 scalability 出问题时最先暴露的短板。
- **开发/修复任务的收口**:走 **§12 verify 门禁**,并把结论落进 `spec.md` / `implementation.md`。
- **快速定位**:系统已经出现症状时,先查上面的"速查表",再回到对应章节展开检查。
- **复审**:每次大促/上线后,回来更新一下容量数字(第 0 节)、infra 快照(§0.2)和验证结果(第 10 节),让清单跟系统实际状态保持同步。
- **取数优先级**:任何"这个系统能扛多少"的讨论,**先去监控平台和 infra 清单取真实数据**(§0.1/§0.2),取不到再问人 —— 凭印象讨论容量是最浪费时间的做法。
