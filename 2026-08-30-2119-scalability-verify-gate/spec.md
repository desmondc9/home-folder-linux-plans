# 开发流程加装「性能验收门禁」+ scalability 清单重构

**日期**: 2026-08-30
**性质**: 家目录规范文件维护(`~/CLAUDE.md` 开发流程 + `~/docs/scalability-review-checklist.md` 重构)
**改动文件**: `~/CLAUDE.md`、`~/docs/scalability-review-checklist.md`(两者均不在任何 git 仓库内,本档案是唯一的变更记录)
**结论**: 把「性能」从"想起来才做的事后审查"改成**流程里的三个固定动作**——设计期取真实数据(Step A)、计划期写死性能决策(Step B)、提 PR 前过门禁(新增 Step E);清单本身从 11 节扩到 13 节,补进一批来自真实生产事故的教训。

## 1. 起因与目标

用户要求:今后在**开发实现**与**前期规划设计**过程中,都要在最后 verify 阶段做一次检查以避免性能问题。三条具体诉求:

1. 清单 §0「先定量:容量预估」要说清楚**数据从哪来**——有 monitoring / tracing / logging 且能访问的(Azure、GCP、Grafana 等),直接去取基础数据;没有再问用户。
2. 再加一个步骤:**摸清项目实际用的 infra**,方便做容量预估。
3. 从某企业级项目仓库的记忆/事故档案中提炼还该写进清单的注意点。

## 2. 现状分析

改动前:

- `~/docs/scalability-review-checklist.md`(139 行,11 节)是一份**通用架构评审清单**,内容正确但偏"教科书条目",没有取数方法、没有 infra 盘点、没有和开发流程挂钩。
- `~/CLAUDE.md` 的「Development, testing, & debugging workflow」有完整的 Step 0/A/B/C/D/D+/E/F 循环,但**质量门禁只有单元测试与契约测试**;性能问题只在 "Reference checklists" 里被动提了一句"被要求评审时用"。

即:清单存在但**没有任何流程触发点**,所以实际上只在出事后才被翻出来。

## 3. 方案

### 3.1 `~/CLAUDE.md` — 三个触发点

| 位置 | 改动 |
|---|---|
| **Step A**(Brain Storming) | 新增产出物「capacity & infra baseline」:① 基线数字**优先自己去可观测性平台取**(GCP / Azure / Grafana+Prometheus / Datadog / Sentry / 数据库统计视图),只读凭据,写操作先问人;取不到才问用户,且问清单 §0.1 里的具体问题。② **infra 家底盘点**(算力/DB/缓存/MQ/网关+WAF/存储/调度/网络/环境阶梯/硬限制),优先只读 CLI 遍历而不是问人。两者都要在 spec.md 注明来源环境与日期。 |
| **Step B**(Write the plan) | 触及数据访问/批量写/异步/缓存/外部调用的 phase,必须在计划里写死性能决策(索引及其上线方式、分页策略、分块大小与其依据的参数上限、各层超时、缓存 key 粒度与失效路径、租户谓词)。 |
| **Step C**(Implement) | 新增第 7 条:清单 §1–§8 当编码红线(非 SARGable 谓词、`ORDER BY` 无 LIMIT、无界 `findAll`、拼串 SQL 破坏计划缓存、批量 DML 分块、租户谓词、超时)。 |
| **Step E**(新增,强制) | 「Performance & scalability verify gate」——走清单 §12:触发器判定 → 逐条给结论 → 写进 spec.md/implementation.md 的「性能与容量」一节 → 未修的记 follow-up。未触发也要在 PR 里写明理由。 |
| **Step F / G** | 原 Step E(Update docs)、Step F(Submit PR)顺延为 F / G;全文 4 处交叉引用同步更新;PR 描述新增"性能门禁结论"一项;收尾确认项新增"门禁已跑且已提交"。 |

**为什么单独立一个 Step 而不是塞进 Step D**:Step D 是"测试是否通过"(功能正确性),门禁问的是"这次改动会不会在生产数据量下变慢"(容量正确性)——后者本地全绿也照样不成立,混在一起会被当成打勾项跳过。

### 3.2 `~/docs/scalability-review-checklist.md` — 重构

结构从 11 节 → 13 节:

- **§0 拆成三段**:§0.1 数据从哪来(六档决策顺序 + 各平台取数速查表 + **七条取数方法学的坑**)、§0.2 infra 家底盘点(十项清单 + 硬限制专表)、§0.3 才是原来的那几个数字(并补了"当前配置理论上限还剩几倍余量""多租户看单租户最大值")。
- **§8 扩写为「边缘与传输层(LB / WAF / 网关 / CDN)」**:WAF 是可用性风险,提到与 §12 门禁同级。
- **§12 全新**:「Verify 阶段性能门禁」= 触发器(9 条) + 收口检查(16 问,分查询侧/写入侧/异步并发/缓存契约/观测验证五组) + 产出物规格。
- **速查表**从 6 行扩到 14 行,补进"零日志全服务无响应""都卡在同一个整数秒""后端查不到日志的 403""发版后白屏但监控全绿"等无法从症状直觉推导的条目。
- **§0.1 取数坑七条**(均来自实测):双窗口(24h + 30d,单看 24h 会错过故障期)、分位数按天对齐(单桶 30 天 `ALIGN_PERCENTILE` 失真)、剔除设计上就长耗时的基线(change-stream 长轮询霸榜)、服务端延迟≠用户体感、延迟指标看不见的故障类型、把发版时间线叠上去做二分、按 avg × execs 排序而不是按 avg。

### 3.3 从生产事故档案提炼进清单的教训(脱敏)

来源是某企业级 GCP + 分布式 SQL 数据库项目的调查报告、审计清单与事故复盘。已去掉全部项目/租户/域名/工单标识,只保留可复用的技术结论:

| 教训 | 落到清单哪一节 |
|---|---|
| DB CPU 均值 ~2% 但查询 100–186s ⇒ 不是容量问题,是单条查询设计问题 | 速查表 + §3 |
| 热表**零二级索引**(扫 92 万~5590 万行)与另一张表 **54 个索引**(写放大)并存 ⇒ 索引要**双向审** | §3 |
| 索引上线是与代码发布解耦的独立写操作;多租户系统里"某国专用索引"不能全量建 | §3 |
| 非 SARGable 全家桶:前导 LIKE / 函数包裹列 / `!=` / `NOT IN(子查询)` / `STRPOS()>0` | §3 |
| 拼串 SQL 除注入外还**击穿查询计划缓存** | §3 |
| 无界 `findAll()` 后内存过滤(同一服务 8 处,下推方法就在旁边) | §3 |
| 批量 DML 撞 DB 单语句参数上限(~950)⇒ 固定分块 + 断言分块数的单测 | §0.2 硬限制 + §3 + §12 |
| 乐观锁只覆盖了手写 SQL,ORM `save()` 那条路会静默覆盖(533 update 仅 95 带保护;24 实体仅 1 个 `@Version`) | §3 |
| 报表/列表/导出 **0 处**用陈旧读,全打在强一致主节点 | §3 |
| 仪表盘四条聚合每条扫 210 万行 × 30 天 4 万次(每分钟自动刷新)⇒ 预聚合 + 别留"今天走实时全扫"的后门 | §5 |
| 后台 push-handler 与用户请求**同实例**,量涨 15× 且每条卡 15s ⇒ 连坐把用户 p95 抬到 6–10s | §5 |
| 一批请求精确卡在 15.00s ⇒ 存在隐藏的应用层 deadline → 超时→死信→重投风暴 | §5 + 速查表 |
| outbox 轮询优先换 CDC/change-stream;必须轮询则谓词列有索引 + LIMIT | §5 |
| 方法体内 `new` 虚拟线程 executor + 驱动内部大量 `synchronized` ⇒ carrier 池(进程级全局、大小=CPU 配额)被 pin 满 ⇒ **整个服务冻结且零日志** | §6 + 速查表 |
| 缓存 key 粒度按"失效成本"选(选能 O(1) `DELETE` 的粒度,避免 `SCAN`);Redis 故障必须非致命 | §4 |
| WAF 在 LB 层拦截 ⇒ 后端零日志;双重编码 payload 命中 SQLi 特征、multipart 上传要求路径含白名单片段 | §8 + 速查表 |
| SPA hash chunk 发版后 404 ⇒ 用户白屏,而 404 只要 0.07s、延迟指标全绿 ⇒ 只能靠 `/js|/css` 4xx 日志指标 + 前端 RUM | §8 + §9 + §0.1 |
| 全局异常处理器对部分异常分支**不打日志** ⇒ 查不到日志 ≠ 没发生 | §9 |
| CI 的 `-Dmaven.test.failure.ignore=true` 放过了导致启动崩溃的真实回归 | §10 |
| 大表 `ADD COLUMN ... DEFAULT` 的 backfill 会撑爆启动探针窗口 ⇒ 迁移与启动解耦 | §11 |
| 缺租户谓词**既是越权也是全表扫描**;序列化推导出的字段名漂移(`gNumber`→`gnumber`)全链路无报错 | §11 |
| 治理方法论:全量机械扫描反模式计数 **与生产慢查询对账**,而不是抽样 | §3 结尾 |

## 4. 关键决策

1. **"先查监控再问人"写成决策顺序表而非一句原则** —— 六档(APM → DB 统计视图 → 网关日志 → 前端 RUM → 压测/类比 → 问人),每档注明适用场景,避免退化成"反正问用户最快"。
2. **infra 盘点独立成 §0.2 而不是塞进 §0.1** —— 它是容量预估的**分母**,和"取当前流量数字"是两件事;而且它的产出物(实测快照表)可长期复用于发布、排障、成本审查。
3. **§12 门禁给"未触发"留了显式出口** —— 纯文案/文档/测试重构必须能一句话跳过,否则门禁会因为太重而被整体绕开。
4. **清单里的实战教训保留具体数字**(5590 万行、54 个索引、15.00s、0.07s)—— 数字比形容词更能让人认出自己正在踩同一个坑;但**不保留任何项目标识**(本仓库公开)。
5. **不把这些教训搬进 `~/CLAUDE.md`** —— CLAUDE.md 每次会话都进上下文,只留流程与指针;细节留在清单里按需读。

## 5. 验收标准

- `~/CLAUDE.md` 的 Step 字母序列自洽,全部交叉引用指向正确的新字母(改动后复查 4 处)。
- 清单 §0.1 覆盖 GCP / Azure / Grafana 三家(用户点名)+ 数据库原生统计 + 前端 RUM。
- 清单存在独立的 infra 盘点步骤(§0.2)且含硬限制专表。
- 事故档案中的教训逐条有归属章节。
- 本仓库公开:成品无任何客户/项目/域名/工单标识,gitleaks 干净。
